# Architecture

This describes the **target** architecture that the codebase is being migrated to.
Until the migration in [Migration plan](#migration-plan) is finished, some parts still follow the prototype; [status.md](status.md) says which.
Each subsystem section says what it does, why it is built this way, and what can go wrong.

## Overview

The product is a static, content-driven site with one persistent interactive globe.

```text
content pipeline (offline)          site (static, Next.js)
--------------------------          -------------------------------------------
sources + Claude + geo data   -->   content/en/*.json  -->  pages  -->  reading panel
        |                                  |                   \
   validation gate                    search index              MapScene --> globe controller
```

The central contract is the **content schema**.
The pipeline produces it, the site renders it, and a future live-answer service will produce the same shape.
The globe never knows where content came from; it only renders a `MapScene`.

## Platform

Next.js App Router with static generation, deployed as a static site on Vercel.

Why:

- Every country and question gets a real path (`/singapore/shipping`) that is prerendered.
  Shared links get proper titles and preview images, and search engines can index the content.
  This matters for a portfolio piece that people will share.
- The root layout persists across navigations, so the globe is created once and never remounts.
- Stage 2 needs server code (live answers, accounts).
  Next.js route handlers add that without changing frameworks.

How it is built:

- `next.config.ts` sets `output: 'export'`, so `npm run build` writes plain static files to `out/` and `npm start` serves them.
  Vercel serves the same folder.
- `app/[country]/page.tsx` and `app/[country]/[story]/page.tsx` are generated by `generateStaticParams` for every map identity (258) and every answered question (30).
  Unknown paths get a static 404.
- URL slugs are mapped to permanent IDs in one place, `src/domain/slugs.ts`, and paths are built in `src/domain/paths.ts`.
  Slugs are readable: the map identity's country slug and the story's `slug` (`/singapore/shipping`, `/united-states`).
- The root layout renders `AtlasShell` (`src/ui/shell/`), which owns the globe, header, map controls, footer, and dialogs.
  Pages only supply the reading panel or the home view as `children`, so navigating never remounts the globe.
  The current page tells the shell its destination and scene through `ShellBridge` (see [Server and client boundary](#server-and-client-boundary)).
- The globe is loaded with `next/dynamic` and `ssr: false`, because it needs `window` and WebGL.
- Trail context stays a search parameter (`/singapore/shipping?trail=water-connects`).
  Pages are prerendered without it and the panel shows trail progress once the page hydrates, which keeps the page itself static.
- Each page sets its own title, description, canonical path and Open Graph preview with `generateMetadata`, through `pageMetadata` in `src/domain/site.ts`.
  Next.js replaces `openGraph` as a whole instead of merging it with the layout's, so the helper always sets all of it.
  The not-found page has no canonical link.
- Absolute URLs (canonical links, `og:url`, robots.txt, the sitemap) are built on `siteOrigin()`: the production domain Vercel sets in `VERCEL_PROJECT_PRODUCTION_URL` for every deployment, or `http://localhost:3000` elsewhere.
  Previews therefore point search engines at production, and Vercel also marks previews `noindex`.
  The value changes when a custom domain is added, on the next deployment, so nothing needs configuring.
- `app/robots.ts` allows all crawling and names the sitemap; `app/sitemap.ts` lists the home page and every published country and question, dated by their review.
  Map-only country pages are left out, because they hold Natural Earth basics rather than edited content.
- The tab icon is a file convention: `app/icon.svg`, plus `app/favicon.ico` for the browser's automatic `/favicon.ico` request, which would otherwise reach `app/[country]`.
  `app/apple-icon.png` is the full-bleed home screen icon for iOS, which rounds the corners itself.

How Vercel serves it:

- The Vercel project uses the Next.js framework preset; its builder detects `output: 'export'` and deploys `out/` as static files, with no functions.
  A local `vercel build` shows what that means: pages are served without `.html` (`/singapore`), a trailing slash redirects to the path without one, and any path that is not a file answers 404 with `out/404.html`, the designed not-found page.
- `vercel.json` holds what static files cannot: response headers, and the prototype query URL redirects described below.
- Caching is left to Vercel's defaults, which already fit.
  Content-hashed files under `/_next/static` are served as `public, max-age=31536000, immutable`.
  Every other file, HTML included, gets Vercel's static default, so the browser revalidates it (a cheap 304) and sees a new deployment at once.
  The basemap, the country geometry and the atlas indexes keep fixed URLs, so they are not marked immutable: a long browser cache would keep stale geometry, or an index whose paths no longer match the pages.
  The site uses system fonts, so there are no font files to cache.
- Every response carries a Content Security Policy that allows same-origin resources only, plus `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and a `Permissions-Policy` that turns off camera, microphone, geolocation, payment, USB and topics.
  Inline scripts and styles are allowed, because a static export carries the React Server Components payload in inline scripts and there is no server to add nonces.
  Framing is allowed, so the site can be embedded in a portfolio; it has no sign-in or actions to clickjack.
  Vercel adds HSTS itself.
- The e2e tests add the headers from `vercel.json` to every page they load (`e2e/fixtures.ts`) and fail on any Content Security Policy violation, so a change that needs another origin fails there first.

What changed from the prototype:

- `vinext` (a beta reimplementation of Next.js on Vite) was replaced by Next.js itself.
- The ChatGPT Sites and Cloudflare Worker template, D1/drizzle scaffolding, and unused shadcn components were removed.
  The three shadcn components in use (dialog, sheet, command) and button live in `src/ui/primitives/`.
- Query-string URLs (`/?country=sgp&topic=shipping&trail=water-connects`) answer with a permanent 308 redirect to the path URL, from `redirects` in `vercel.json`.
  A static page cannot see the query string of the request that loaded it, so the redirect has to happen in front of the files.
  Each rule matches the home path and the query by permanent ID: the country case-insensitively (the prototype accepted `sgp` and `SGP`), the question and trail exactly.
  Rules are ordered most specific first, because Vercel applies the first match: a trail stop keeps its trail, any other question drops it, and any other country URL opens the country, so a question that no longer exists still lands on its country.
  `src/domain/legacy-redirects.ts` builds the rules through `destinationPath`, from the frozen list of questions and trails the prototype published plus every map identity (the prototype had the same 258), and `npm run redirects:build` writes them into `vercel.json`.
  Content added since never had a query URL, so new questions do not add rules.
  `tests/deployment.test.ts` compiles `vercel.json` with Vercel's own routing utilities, matches requests against the result, and fails when the committed rules differ from what the builder produces.
  Vercel passes the original query string on to the destination, so a redirected URL can keep `country` and `topic`; pages ignore them, and a trail the question is not on is ignored too.
  There is no in-browser fallback: Vercel is the only host, and keeping a second copy of the mapping in the client would cost a script and an index fetch on the home page for links that only ever pointed at the prototype.
  Serving `out/` locally (`npm start`, the e2e tests) therefore shows the home page for these URLs.

## Content model

Content lives in `content/<locale>/`, validated against a zod schema in `src/content/schema.ts`.
The loaders parse every file on first use, so a file that fails validation fails the build.
`npm run content:check` and the content tests run the same schema plus the checks a schema cannot express.

```text
content/en/countries/<slug>.json   { country: Country, stories: Story[] } for one country
content/en/trails.json             Trail[]
content/en/places.json             { [placeId]: note }, editorial notes shown on map places
content/en/home.json               { suggestedQuestions: StoryRef[] (3 to 4) }, the home screen's picks
content/en/claims/<slug>.json      claim check results for one country (pipeline only, see Content pipeline)
```

Core shapes:

```text
Country     id, slug, name, nativeName?, region, kicker, overview, quickFacts[],
            starterStoryIds[] (3 to 5), scene: SceneSpec, sources[], provenance
Overview    summary, geography, sourceIds[], whyItMatters[{title, text, sourceIds[]}]
QuickFact   label, value, asOf?, sourceIds[]
Story       id, countryId, slug, question, paraphrases?, category, summary,
            sections[{title, text, sourceIds[]}], takeaway, scene: SceneSpec,
            next: StoryRef[] (max 3), sources[], provenance
Paraphrases question (the wording they restate), phrasings[] (3 to 8, 120 characters each),
            generatedBy, generatedAt, promptVersion?
StoryRef    countryId, storyId, reason? (required when the story is in another country)
SceneSpec   camera?, focusCountryId, highlights[{countryId, role}], placeIds[], routes[], mapNote?
Route       id, kind: sea | land | river | flow, via: placeId[] (2 or more)
Source      id, title, publisher, url (https), accessedAt?
Provenance  generatedBy ("human" or a model ID), generatedAt, promptVersion?, reviewedBy?, reviewedAt?,
            status: draft | reviewed, revision?{notes, requestedBy, requestedAt} (drafts only)
Trail       id, title, label, description, stops[{countryId, storyId, connection}]
Home        suggestedQuestions[{countryId, storyId}] (3 to 4, distinct, shown in this order)
```

Content stores a `SceneSpec`, which only names places.
`resolveScene(spec)` turns it into the globe's `MapScene`: coordinates from the gazetteer, notes from `places.json`, and route polylines along great circles.
A country place marks the part of the country the scene looks at.
Its gazetteer point is Natural Earth's label point, which for a country in several parts can sit far from the story: Malaysia's is on Borneo, while the Singapore stories are about the peninsula.
`countryPlacePoint` in `src/content/geo.ts` takes the label point unless one of the country's interior label candidates (the same points the globe names it at, from `label-candidates.ts` over `public/maps/countries.geojson`) is less than half as far from the scene's center, which is the scene's camera or else the focus country's label point.
The point is still derived from map data, never written by hand.
Place notes are locale text, so they live in content rather than in the generated gazetteer.

Rules:

- Story and country IDs are permanent and never derived from titles or order.
  Every cross-reference uses IDs, never array positions.
  Country IDs are the ISO 3166 alpha-3 codes of the map identities in `data/geo/countries.json`; story IDs are unique within a country.
- Slugs are readable URL segments and may change; IDs may not.
  A country's slug must match its map identity, and its file is named after the slug so content paths match URLs.
- Every section, overview item and quick fact lists the source IDs that support it, and every declared source is cited.
- `placeIds` and route `via` lists reference gazetteer IDs; coordinates are looked up from `data/geo`, never written by hand or by the model.
- `sea` routes must stay at sea (see [Content pipeline](#content-pipeline)).
  `land` and `river` routes follow their named places.
  `flow` routes are illustrative arcs for a relationship such as trade or language, and are not checked against land.
- Each story leads to at least one next question in the same country and one elsewhere.
  A draft may lead to a planned story in a country that has no file yet (see [pending references](#content-pipeline)); reviewed stories may not.
- Generated content records when each source was read (`accessedAt`); content converted by hand (`generatedBy: "human"`) may omit it.
- `paraphrases` are other ways a reader might type a story's question, used only by search and never shown.
  They restate the question and make no claims, so they cite no sources.
  They record the question they were written for; once the story's question changes they fail validation as stale until `npm run content:paraphrase` replaces them.
  No phrasing may repeat the question, another phrasing, or another question in the same file.
- Only `reviewed` content is built into production.
  In production the loaders drop drafts and every starter question, next question and trail stop that points at one; development shows drafts.
- Locale is a directory, so a Chinese edition is a parallel `content/zh/` tree with the same IDs.

Loaders in `src/content/index.ts` are synchronous and server-only (see [Server and client boundary](#server-and-client-boundary)):
`getCountry(id or slug)`, `listCountries`, `getStory`, `getStoryBySlug`, `listStories`, `listTrails`, `getHome`, `getPlaceNote`, `getMapCountry` (all 258 map identities, edited or not) and `resolveScene`.
Content files are discovered, not registered: `readContentTree` in `src/content/files.ts` reads every `countries/*.json` file, ordered by file name, and the known top-level files (`trails.json`, `places.json`, `home.json`) when content is first read.
A file that cannot be read, is not JSON, or does not match the schema fails with its path; an unknown top-level JSON file fails too, so a new kind of content file is added to `TOP_LEVEL_FILES` and the schema together.
Other directories, such as `claims/`, are never read, so the loaders, the build and the static export never see or ship them.
The loaders, `content:check`, the pipeline and the tests all read content this way, from paths relative to the repository root, where Next.js, the scripts and Vitest run.
In development the loaders compare the tree's file sizes and modification times at most twice a second and reload content when they change, so an edited or new file shows on the next page load without restarting the server.

A story scene without a `camera` borrows its country scene's camera when both focus the same country.
Framing from the focus country's area alone is too close for very small countries such as Singapore, and a story's route then leaves the frame.

Why: the prototype keyed Chinese text by array index and spread translations across five mechanisms.
One schema, ID-only references, and locale-as-directory remove both problems.

## Content pipeline

Offline scripts in `pipeline/` research, draft and validate content with Claude, and record Ryan's review.
Nobody writes content JSON by hand.

```text
pipeline/
  config.ts        paths, default model and effort, per-request limits
  content-tree.ts  reads and writes one locale's tree on disk (content/en, or a temporary copy in tests)
  prompts/v<n>/    versioned drafting prompt files; the version is recorded in provenance
  prompts/paraphrase/v<n>/  versioned prompts of the paraphrase step, recorded in paraphrases
  prompts/claims-v<n>/  versioned claim check prompts, on their own version line
  prompts/agent-v<n>/   versioned agent drafting prompts, on their own version line
  prompts/claims-agent-v<n>/  versioned agent claim check prompts, on their own version line
  batches/         batch definitions (pilot.json) and the question plans generated for them
  generate/        plan, draft and redraft (npm run content:generate)
  validate/        every content:check rule plus source URL reachability (npm run content:verify)
  claims/          check text against the sources it cites (npm run content:claims)
  review/          list, read, approve and send back drafts (npm run content:review)
  paraphrase/      search phrasings for each story's question (npm run content:paraphrase)
  agent/           commands a Claude Code subagent drafts a country with (npm run content:agent)
  claims-agent/    commands a Claude Code subagent checks claims with (npm run content:claims-agent)
```

```sh
npm run content:generate -- --batch pilot      # plan, then draft every country in the batch
npm run content:generate -- --country CHL      # draft one country (repeat --country for more)
npm run content:generate -- --revisions        # redraft everything review sent back
npm run content:agent -- start CHL             # or let a Claude Code subagent draft Chile
npm run content:verify                         # content rules and source URLs
npm run content:claims -- CHL                  # check Chile's text against its sources
npm run content:claims-agent -- start CHL      # or let a Claude Code subagent check it
npm run content:paraphrase -- --all            # search phrasings where missing or stale
npm run content:review -- list                 # then show, approve, revise
```

Coverage grows in batches: a pilot batch to tune prompts and the review bar, then expansion.

1. **Plan.**
   A batch run first asks for a question plan for every country in the batch, in one structured-output request, and writes `pipeline/batches/<batch>.plan.json`.
   Ryan can edit the plan before drafting; `--plan-only` stops after planning and `--replan` replaces the plan.
   Planned story IDs are permanent: drafts must keep them, and next questions in other countries link to them.
2. **Draft.**
   Each country is one conversation with Claude Opus 5.5 (`--model` to change) with adaptive thinking at `high` effort (`--effort`).
   [Agent drafting](#agent-drafting) does the same work in a Claude Code subagent instead, with the same checks.
   Research uses the server-side web search and web fetch tools.
   Places come from the gazetteer: the system prompt lists every water body and country, the task lists cities and regions in and near the country, and a `find_places` tool searches the rest.
   The draft is submitted through a tool (`submit_draft`) whose schema carries every constraint, then parsed with zod and checked with every `content:check` rule inside the current tree.
   The tool is not strict: the API refuses to compile a whole country draft into a strict grammar, so a shape mistake goes through the repair loop like any other problem.
   The pipeline adds its own rules: every cited URL came back from a search or fetch in the same conversation, next questions point to existing or planned stories, planned and inbound story IDs are kept, a country has 4 to 6 stories, and text is English.
   Problems go back to the model as a tool error, up to three repairs; a job that still fails saves its last draft and log in `pipeline/.cache/failed/`.
   The pipeline fills in what the model does not write: known IDs, each entry's own source list with tracking parameters removed from its URLs, `accessedAt` (the run date) and `provenance: { generatedBy, generatedAt, promptVersion, status: 'draft' }`.
   The model never sets a camera; the globe frames the scene.
   An existing draft is replaced only with `--regenerate`, and a file with reviewed content only with `--force`.
3. **Verify.**
   `content:verify` runs every `content:check` rule, lists pending references, and checks every source URL.
   A URL is ok (2xx), broken (404, 410 or an unknown host; fails the command) or unverified (401, 403, 429, 5xx or a timeout; a warning to open by hand).
   Some sites refuse every automated request with a bot challenge; after a person opens such a page and finds it supports the content, its exact URL goes in `KNOWN_BLOCKED_URLS` in `pipeline/config.ts` with the date, and a 401, 403 or 429 from it then counts as ok.
   An entry never excuses a 404, 410 or dead host, never covers a whole site, and lapses after 180 days, when the page is a warning again until someone reopens it.
   It tries HEAD then GET, retries twice with backoff, limits requests per host, and caches results in `pipeline/.cache/url-status.json` (ok for 30 days, others for a day).
   `--offline` skips the network and reports cached results.
4. **Claims.**
   `content:claims -- <country> [story]` (or `--all`, or `--drafts`) asks Claude whether the cited sources state each piece of text.
   [Agent claim check](#agent-claim-check) does the same check in a Claude Code subagent instead, with every quote verified against a live fetch.
   A unit is one claim-bearing piece with its source IDs: the overview's summary and geography together, each why-it-matters point, each quick fact (with its as-of date), and each section of a story.
   A conversation with Claude Opus 5.5 at `high` effort (`--model`, `--effort`) checks the due units of one country; checking one story alone is its own conversation.
   Every cited page stays in the conversation's context, so a country's due units are packed into conversations that cite at most `CLAIM_SOURCES_PER_SESSION` sources each (10, `--sources-per-session` to change), with overviews and stories that share sources kept together so a shared source is read once.
   The bound leaves room in the 1M-token context window: 10 pages at the 60k-token fetch cap are at most 600k tokens, while the pilot's pages averaged 15k to 39k tokens each, so Russia's 24 sources in one conversation reached about 930k tokens and Nigeria's 37 did not fit.
   Packing is greedy: a conversation starts from the overview or story citing the most sources and keeps taking the one that adds the fewest new sources while it fits; one that cites more than the bound on its own is split by its units.
   Most countries need one to six conversations; their tags are `claims-<country>-part<n>`.
   Claude reads every cited source with the server-side web fetch tool in its basic version, which puts the page in context; the newer version with dynamic filtering reads pages from code and kept too little text to judge a claim.
   Some sites refuse Anthropic's fetcher but answer an ordinary request, so a strict `fetch_page` tool fetches a cited URL of the task from the editor's computer and returns the page's visible text; it reads HTML and plain text, not PDFs, and runs no scripts.
   Verdicts come back through a strict tool, `submit_verdicts`: for each source whether it was read (with a note when not), and for each unit `supported`, `partly_supported`, `not_supported` or `source_unreachable`, the phrases the sources do not state, short quotes from the sources that support the rest, and a note.
   The pipeline checks the submission and sends problems back like a draft's: every unit and source answered once, a source reported read was actually fetched in the conversation, `supported` has no unsupported phrases and the others do, every unsupported phrase is copied from the unit, quotes come from the unit's own read sources, and `source_unreachable` names an unreadable source.
   Every quote must also appear in the text the conversation was given for its source (a web fetch served as text, or `fetch_page`'s text).
   Both sides are normalized before matching (`normalizeForMatch` in `pipeline/claims/verdicts.ts`), so only the words and numbers must agree.
   Literal `\uXXXX` and backslash escapes the model sometimes writes are decoded; every quotation mark and apostrophe variant is folded, and kept only inside a word (`it's`), so a quote may add or drop the quotation marks around a phrase.
   Unicode compatibility forms are folded (no-break and narrow spaces, `…`, superscripts), soft hyphens, zero-width characters and private-use characters are dropped, every dash and the minus sign become a hyphen with no space around it, and case and whitespace are ignored.
   Private-use characters have no standard meaning; a PDF font may draw a symbol with one (a Gawecki paper has U+F0AB in its text), and a quote copied from a display leaves it out.
   A space before closing punctuation (`, . ; : ! ? % ) ] }`) or after an opening bracket is dropped on both sides, since some pages write "1990 , and" and a quote that drops the space is the same words.
   Web fetch serves pages as Markdown, so link targets, emphasis marks and table pipes are dropped too: a quote of "Capital: Moscow" matches `Capital: [Moscow](https://...)`.
   "..." (or "[...]") marks a gap: the pieces must appear in order, with at most `QUOTE_MAX_GAP` (300) normalized characters, about 50 words, between consecutive pieces, so a quote cannot stitch together words from distant passages of a page; a quote whose pieces are farther apart goes back with that reason.
   On the recorded runs of nine countries the widest gap in a matching quote was 30 characters.
   Three rules apply only to the marks the local fetcher leaves in a PDF's text (see the `fetch` command in [Agent drafting](#agent-drafting)), so they change nothing on a page without them.
   A `[Page n]` line on a line of its own is skipped, so a quote may run across a page break.
   A word hyphenated at a line break (a letter, a hyphen, a line break, a letter) matches the quote with the hyphen or without it, since the text cannot tell "govern-ment" from "self-government".
   A NUL, which some PDFs give for the "fi" and "fl" ligatures, matches "fi" or "fl" in the quote.
   A quote must be under 30 words (`QUOTE_MAX_WORDS`, 29, counting the runs that hold a letter or digit), as the prompts and the schema have always asked, and a longer one goes back with the request to quote only the words that state the claim.
   A quote that is not on the page goes back with where it parts from the page: the longest start of its first missing piece that is on the page, what the page has next and what the quote has instead, shown as compared (lowercase, with spacing, quotation marks and dashes folded); or that each piece is on the page but not in that order; or that nothing on the page starts like it.
   A PDF comes back from the server as a document whose text the pipeline does not extract, so quotes from a PDF are not checked.
   On the recorded Singapore and Japan runs, 38 of the 39 checkable quotes matched; the other was a description of a table row, which the check now sends back.
   On the recorded United Kingdom, Russia and Netherlands runs, the Markdown and quotation mark folding removed 16 rejections, each a real match, and introduced none; all three now pass on replay.
   Problems are tied to the units they affect: a unit whose own answer has a problem, or that cites a source answered wrongly, fails, and the others pass.
   Each submission's passing verdicts are saved at once, and a unit keeps its latest passing verdict even if a later submission garbles it, which happens on repair turns, where the model sometimes mangles non-ASCII characters in a quote.
   Results are committed with the content in `content/en/claims/<slug>.json`, keyed by a hash of the unit's text and its sources' IDs and URLs, with the verdict, model, effort, prompt version and date; `--claims-dir` points a scratch run elsewhere.
   Changed text or sources make a new key, so the old result no longer counts and the unit shows as not checked; a run checks only units without a result for their current text, with their overview or story as context, and `--recheck` checks every selected unit anyway.
   Every write keeps only the results of the file's current units, in content order, with fields in a fixed order and the content tree's JSON formatting, so a recheck or an approval makes a small, readable diff.
   A conversation that ends without a verdict for every unit (repairs exhausted, an API error, the request limit) is `partial`: its passing verdicts stay saved, and each remaining unit is reported as not checked with its reason.
   Its log goes to `pipeline/.cache/claims-failed/<tag>.json` with the reason, the unchecked units and their reasons, the conversation and the last submission.
   Running the same command again checks only the unchecked units.
   A conversation that outgrows the context window ("prompt is too long") is not fatal to the run: its verdicts so far are saved and its unchecked units go to two or more smaller conversations in the same run, each citing about half the sources (`<tag>-split<n>`), until they fit or a unit cannot be split further and is reported as not checked.
   A submission in the last allowed request still counts.
   The command prints every flagged unit, groups the unchecked units by reason, and exits with an error when a unit is flagged or not checked.
   `--mode batch` sends each round through the Batches API at half price; unlike drafting it has no `--resume`: verdicts are saved as each submission passes, and an interrupted run checks only what is still due.
   The prompts live in `pipeline/prompts/claims-v<n>/` on their own version line, so changing them never changes the drafting prompt version.
5. **Paraphrase.**
   `content:paraphrase -- <country>...` (or `--all`) writes [paraphrases](#content-model) for every story that has none or whose question changed since they were written; `--regenerate` replaces current ones too, and `--dry-run` lists the stories without calling the API.
   Each country is one small structured-output request (Claude Opus 5.5 at `low` effort by default, `--model` and `--effort` to change), a few countries at a time.
   The task gives each story's question, category and reviewed text, and lists the country's other questions so phrasings stay apart from them; the response schema allows only the IDs asked for.
   The story's text grounds the phrasings: they may use the places, people and terms it names, since readers search by those, but add nothing it does not say and take no side it does not take.
   The response must cover every story asked for, in English, and pass every content rule for paraphrases; problems go back to the model, up to two repairs, and a country that still fails is left as it was.
   The step writes only `paraphrases` (with the model, date and `paraphrase/v<n>` prompt version), never a story's text, sources or provenance.
   Paraphrase edits do not reset review: they restate a reviewed question and make no claims, so there is nothing new to source-check, and review shows them so a misleading phrasing can still be caught.
   Drafts never carry paraphrases: drafting prompts show the reference example and a story under revision without them, so they stay byte-identical to what a drafting run in progress already sent, and a redrafted story loses its old ones, so run this step after generating.
   Its prompts are versioned apart from the drafting prompts (`CURRENT_PARAPHRASE_PROMPT_VERSION`), so changing them never touches `CURRENT_PROMPT_VERSION` or a resumable drafting run.
   Expect a few cents per country.
6. **Review.**
   `content:review -- show <country> [story]` prints the questions, sections with their sources, the map scene by place name, next questions, search phrasings, validation warnings, and under each unit its claim check: the verdict, what the sources do not state, unreadable sources, and the supporting quotes.
   A summary counts the verdicts and lists what blocks approval; `--check-urls` checks the file's URLs first.
   `approve <country> [story]` sets `status: 'reviewed'`, `reviewedBy` (`--by`, default the git user name) and `reviewedAt`.
   Without a story it approves the overview; `--all` approves the overview and every story.
   It refuses while the content has a validation issue, a pending reference, a revision request or a broken source URL.
   It also refuses while a unit has no current claim check, or a unit is flagged: `partly_supported`, `not_supported` or `source_unreachable`.
   A flagged unit either goes back through `revise`, or Ryan opens the sources, finds the claim stated (for example on a page the check could not read), and approves with `--accept-claims "<why>"`, which records who accepted it, when and why on that result in `content/en/claims/`, so the decision is committed with the approval.
   `--accept-claims` never excuses a unit that has no current check.
   An acceptance belongs to the exact text and sources, so it lapses when either changes.
   `revise <country> [story] --notes "..."` records `provenance.revision`, and `content:generate -- --revisions` redrafts it: a story keeps its ID and the rest of the file, with the notes and the old story in the prompt.
   A whole country can be sent back only while nothing in it is reviewed.
   Changes go through notes and regeneration rather than JSON edits, so every text stays sourced.
7. **Commit.**
   Reviewed JSON is committed like code, with its claim check results in `content/en/claims/`; git history is the content history.
   A new country file needs nothing else: the loaders discover it.

Pending references: a draft story may link to a planned story in a country that has no content file yet, so a batch can link its countries before all of them are drafted.
`findPendingReferences` in `src/content/validate.ts` lists them; `content:check` accepts them in drafts and rejects them in reviewed stories, and review will not approve a story that has one.
They resolve when the target country is drafted, because its draft must keep the planned IDs.

Cost controls:

- Prompt caching: the system prompt (instructions, the Singapore file as a reference example, the shared gazetteer) and the list of link targets are identical for every task in a run and end in cache breakpoints, and automatic caching covers the growing conversation.
  History is append-only so later turns keep reading the cache.
- Limits per job in `pipeline/config.ts`: 12 searches and 16 fetches per request, 3 repairs, 2 reminders to submit, 6 research continuations, 24 requests, and the model's 128k output tokens per request.
- `--mode batch` sends each round of requests through the Message Batches API at half price with a 1-hour cache lifetime.
  The run state is saved in `pipeline/.cache/batch-run.json`, and `--resume` continues an interrupted run.
  `--resume --mode sync` collects the round in flight, then finishes each conversation one request at a time, for when batch rounds queue for hours.
  Synchronous runs use server-side fallback models when a request is refused; batch runs cannot.
- Every job prints its token usage, searches and estimated cost, and the run prints the total.
  Measured on the pilot at `max` effort in synchronous mode, a country cost about $9 (from about $7.30 to $12), with cache writes counted from every iteration of a server tool loop; that is about $180 for a 20-country batch, less at `high` effort, and batch mode about halves the token part.
- A claim check costs what its fetched pages cost to read.
  Measured at `high` effort: Singapore (14 units, 13 fetches, a 125k-token statistics PDF among them) about $2.50 with one conversation per overview and story, and Japan (13 units) about $9.70, because each of its four conversations read the same 475k-token statistics handbook PDF; packing by shared sources reads such a page once.
  Every request rereads the whole conversation, so a conversation of 10 sources costs less per request than one of 30, and smaller conversations repay the few sources two of them share.
  Its limits in `pipeline/config.ts`: at most 10 cited sources per conversation, one fetch per cited page plus 4 retries per request (at least 16), with at most 60k tokens of text each, 2 repairs, 2 reminders, 3 continuations and 10 requests per conversation, 4 conversations at a time.
  PDFs ignore the 60k cap, so a long statistics PDF can cost far more than a web page, and can still overflow a conversation, which is then split again.

The API key comes from `ANTHROPIC_API_KEY` in the git-ignored `.env.local` (copy `.env.example`); without it a real run stops before doing any work and says so.
Only the pipeline uses it: the site, its build and CI need no keys, so it is never set on Vercel or GitHub.
`--record <dir>` saves every response as `<dir>/<tag>/<n>.json` (and the claim check's local page fetches in `<dir>/pages/`), and `--replay <dir>` answers requests from such a directory without network or key.
The end-to-end test replays `tests/pipeline/fixtures/replay` (placeholder text, built by `build-replay.ts` in the same folder), and the same fixtures run from the command line:

```sh
cp -R content/en /tmp/elsewhere-en
npm run content:generate -- --country CHL --replay tests/pipeline/fixtures/replay --content-dir /tmp/elsewhere-en
npm run content:verify -- --offline --content-dir /tmp/elsewhere-en
npm run content:review -- show CHL --content-dir /tmp/elsewhere-en
```

The claim check fixtures cover only the Chile overview and one story, so they run in the tests rather than from the command line.

Geo data in `data/geo/` is generated from Natural Earth 10m datasets, which are cached in `.map-sources/` and recorded with URL and SHA-256 in `data/geo/sources.json`:

- `countries.json` (`npm run maps:countries`) holds all 258 map identities: ID, slug, English name and short map name, region, population and label anchor.
- `gazetteer.json` (`npm run maps:gazetteer`) holds about 1,260 named places (37 KB gzipped): every country, named seas and straits, major rivers, physical regions, and major cities and capitals.
  IDs are slugs of the English name; when two kinds share a name, the lower-priority one gets a suffix, so `singapore` is the country and `singapore-city` the city.
- `gazetteer-overrides.json` is the only hand-maintained input: a short list of extra Natural Earth features to include, renames to common English names, extra passages, canals, and the few features Natural Earth lacks.
  Added features are anchored to Natural Earth geometry, never to typed coordinates, and every entry gives a reason.
  The Suez and Panama canals come from Natural Earth's river and lake centerlines, which have no marine polygon for them.
  The Strait of Hormuz, which Natural Earth draws only as the line where the Persian Gulf and Gulf of Oman polygons meet, is labelled at the middle of that line.
  The Drake Passage, whose Natural Earth polygon is only slivers along the Antarctic shore, is placed the same way where the Pacific and Atlantic polygons meet south of Cape Horn.
  Cabot Strait is the middle of the shortest line between the Cape Breton Island and Newfoundland region polygons, and the Celtic Sea is the part of the North Atlantic polygon near where the Irish Sea, the Bristol Channel and the English Channel meet it.
  Natural Earth has the Saint Lawrence twice (the estuary polygon and the river centerline); a rename merges them into one ID, `saint-lawrence-river`, the estuary with its passage path.

Sea routes are checked against `public/maps/countries-detail.geojson`, the detailed geometry the globe draws; the base geometry's coarser coastlines close narrow straits such as the Bosporus.

- Every sea place has a label point that is at sea in that geometry.
  A water body whose polygon is entirely covered by simplified land is dropped (currently only the Luzon Strait).
- Straits, channels, canals and a few listed gulfs (the Gulf of Suez, the Gulf of Saint Lawrence) are passages: they get a passage `path`, and a route through one follows it end to end, because a single label point inside a winding strait forces the line across a shore.
- A strait's path is traced by `scripts/passage-paths.mjs`: the cheapest way through its water on a grid of 0.5 to 4 km cells, from one end of its long axis to the other, preferring cells far from shore so the path keeps to mid-channel, then simplified without adding land.
  Natural Earth's marine polygons are drawn loosely (some straits are only slivers along each shore), so the path may use open water up to 30 km outside the polygon, and each end moves to open water nearby.
  Where the axis does not reach the real entrances (the Northwest Passage archipelago, the bending Strait of Magellan), the overrides set the ends where the polygon meets two named water bodies.
  Where the polygon is unusable (the Drake Passage), the path runs through the two oceans' water within 500 km of where they meet.
  A canal's path is its centerline.
- A route is sampled along great circles every 2 km.
  Land within 50 km of a land waypoint (a port) is allowed, and crossings of 15 km or less are ignored, so small islands do not fail a route.
- Segments between points of one passage path are not sampled: the build traced them through the passage's water.
  Marine passages stay off the globe's land (a test checks every one), canals cross the land they cut through, and the build prints any other passage that crosses land the geometry closes (only about 1 km of the Saint Lawrence River).
  The legs into and out of a passage are checked like every other segment, so a route that skips a passage still fails.
- A port next to a passage in a route is on it (Punta Arenas on the Strait of Magellan, Istanbul on the Bosporus): the route leaves the passage at the path point nearest the port, or joins it there, instead of sailing to the far end and back across the land.

What can go wrong:

- Model-written coordinates and routes are often wrong, for example a "sea route" drawn across a peninsula.
  This is why places come from the gazetteer and routes are checked against land polygons.
- Ocean label points sit in the middle of the ocean, far from most scenes.
  Prefer the nearest marginal sea (the Philippine Sea rather than the Pacific) when a story means the water off a coast.
- Gazetteer label points are only as good as the named places near a coast: the gazetteer has only major ports (scalerank 2 or less, capitals, and the few the overrides add), so a realistic route may need a port or water body the gazetteer lacks and fail the land check.
  Add the Natural Earth feature through the overrides rather than drawing a `flow` route.
- Ocean label points are far from coasts, so a route that starts in an ocean (the South Atlantic into the Strait of Magellan) can cross land on its way to the passage; start from the nearest marginal sea or island instead.
- A URL that resolves does not prove it supports the claim; the claim check reads the page, and review still decides.
- The claim check is a model reading pages, so it can miss a statement or misread one.
  Quotes from PDFs are not checked, and a page that needs scripts to show its text, or that blocks both fetchers, comes back unreachable and needs a person.
  Quote matching ignores case, quotation marks, dashes and Markdown, so a quote can differ from the page in those and still pass; its words and numbers must match exactly.
  In a PDF's text a NUL matches either "fi" or "fl", so a quote could read "flat" where the page has "fiat"; the letters around it must still match, and the subagent is asked to write the real word.
  A flag means "open this source", not "this is false": most flags on the hand-converted countries are true facts cited to a page that does not state them.

### Agent drafting

`npm run content:agent` lets a Claude Code subagent draft a country in place of an API conversation, so drafting is paid by a Claude subscription instead of API credit.
The subagent researches and writes; the pipeline keeps every guarantee of the API path and makes the evidence rule stricter.
`.claude/agents/content-drafter.md` defines the subagent: Opus, with Bash, Read, Write, Edit, Glob, Grep and WebSearch, and without WebFetch.
Ask Claude Code to run it for a country; one subagent drafts one country, and several can run at once.

```sh
npm run content:agent -- start CHL [--content-dir <dir>] [--model <id>] [--date YYYY-MM-DD] [--regenerate] [--fresh]
npm run content:agent -- fetch CHL "<url>" [--offset <n>] [--find <words> | --links] [--refresh]
npm run content:agent -- places CHL [--query <name>]... [--country <map ID>] [--near <place ID>]
npm run content:agent -- submit CHL [<draft.json>] [--dry-run]
npm run content:agent -- status CHL
```

- `start` creates `pipeline/.cache/agent/<country>/` with `session.json` (country, content directory, model, prompt version, date, and logs of submissions and failed fetches) and `brief.md`, the subagent's complete instructions.
  The brief is the system prompt, the reference example, the shared gazetteer, the link targets and the country task, built by the same functions as the API task, followed by the JSON Schema of the submission.
  Its prompts are their own version line, `pipeline/prompts/agent-v<n>/`: agent-v1 is v3 with the research, tool and submission instructions rewritten for these commands, and every content, tone and sourcing rule unchanged.
  agent-v2 is agent-v1 with the research section made current: it recommends sources the fetch command can read (national statistics offices, government and parliament pages, international organizations, museums, archives, libraries, open pages of academic publishers and reputable news), because Britannica refuses the local fetcher and the CIA World Factbook is discontinued.
  It adds three instructions: read pages only through the fetch command and never with curl, wget or another HTTP tool, use `--links` to find documents, and never put personal information (names, email addresses, domains) in any request.
  agent-v1 stays as it was for the ten drafts that recorded it; a session keeps the prompt version it started with.
  A draft records `promptVersion: "agent-v2"` and the session's model (`claude-opus-5-5` by default) as `generatedBy`, so agent drafts can be told apart from API drafts.
  Running `start` again continues an unfinished session with its evidence and rebuilds the brief; `--fresh` discards the session first.
  It refuses a file with reviewed content, and an existing draft that review did not send back unless `--regenerate` is given.
- `fetch` reads a page from the editor's computer with `fetchPage` in `pipeline/claims/local-fetch.ts`: HTML and plain text as the server returns them, without scripts, and PDFs by their text layer with a `[Page n]` line before each page.
  PDFs are read with unpdf, a maintained packaging of Mozilla's pdf.js for Node with no dependencies of its own.
  pdf.js runs at verbosity 0 (errors only), so its font warnings ("TT: undefined function") never mix with a command's output.
  Some PDFs draw their text twice, as a second text layer or to fake bold (Nunn and Qian's paper draws every line twice), and read in drawing order each line runs into a copy of itself.
  A run of text is dropped as a copy when it lies on the same baseline, in the same size, within the stretch of longer runs it overlaps, and its letters are among theirs, since two different texts are never drawn over each other; the copies are not always split into runs the same way, so longer runs are kept first.
  Running headers and footers are kept once: a line among the first or last three of at least two in five pages (and at least three pages) that is the same on each, or differs only by the page number, stays where it first appears and is dropped from the pages after.
  No text is lost that way, and a sentence that runs on from one page to the next reads on with only the `[Page n]` line between, which the quote matcher skips; a table's "Total 1,204" and "Total 1,388" are different lines and both stay.
  Some PDFs map the "fi" and "fl" ligature glyphs to U+0000 in their own ToUnicode table (Panama's constitution from constituteproject.org does), so "official" comes out as "of", a NUL and "cial"; the letters cannot be recovered from the file, so the text keeps the NUL and the quote matcher reads it as "fi" or "fl".
  HTML character references are decoded once with the `entities` package, which knows every named reference HTML defines ("&eacute;" was left as it was before); a page that escapes its text twice ("&amp;eacute;") shows "&eacute;", as it does in a browser.
  Text is decoded in the charset the Content-Type header names, else the one an HTML page declares in a `<meta charset>` or `http-equiv` tag in its first 2 KB, else UTF-8; a page that declares nothing and is not valid UTF-8 is read as windows-1252, which older government sites such as Argentina's InfoLEG serve without saying so.
  Each page becomes an evidence record in `evidence/`: the requested and final URLs, both normalized, the HTTP status, the content type, the time, the SHA-256 of the text, and the text, up to 2 million characters from at most 40 MB.
  It prints 20,000 characters at a time (Claude Code shows up to 30,000 characters of a command's output), with `--offset` for another part and `--find` to list where words appear; later reads come from the stored copy unless `--refresh` is given.
  Reading a long page part by part with `--offset` is the way to read all of it; there is nothing to save elsewhere, and the stored copy makes each part instant.
  `--find` searches for the words literally, ignoring case, and says how many times they appear; it lists 20 at a time, each with about 150 characters on either side shown with line breaks and runs of spaces as one space, and ends with the command for the next 20, where `--offset` is the character to search from.
  The commands ignore a closed output pipe, so `fetch ... | head` ends quietly instead of with an `EPIPE` error.
  `--links` lists the page's links instead of its text, because the text leaves them out and a drafter otherwise resorts to curl to find a statistics table PDF or a primary source.
  Each line is the anchor text and the absolute URL, `text | URL`, in page order and once per URL (fragments are dropped, an empty anchor takes the text of a later link to the same URL, and links to the page itself, `mailto:` and `javascript:` are left out).
  It pages like the text, 20,000 characters at a time, but `--offset` then counts links, so a part never ends in the middle of a URL.
  The links are kept in the evidence record (at most 5,000 per page) and are not covered by the hash, since they are only a way to find pages; a record stored before links were kept asks for `--refresh`.
  PDFs and plain text have no links.
  A page that answers with an error status, a bot challenge, no text without scripts, a type other than HTML, plain text or PDF, or no answer within a minute stores nothing, so it cannot be cited.
  A server error (5xx) is tried again after 5, 20 and 60 seconds, or after the server's `Retry-After` when that is a minute or less, because usgs.gov answered 504 for longer than subagents kept retrying by hand; any other status, such as the 403 that Britannica, EITI and Wiley answer, is final at once, since asking again would not change it.
  A network failure reports its cause along with "fetch failed" (Node keeps the real reason in `error.cause`), such as a redirect loop, a certificate for another host name, `ECONNRESET` or an unknown host, so a page that will never load is told apart from one that may load later.
  The claim check's `fetch_page` tool shares this reason.
  Every failed fetch is recorded in `session.json` with its URL, time and reason, and `status` lists it, so a drafter sees which pages failed and why.
  A failed fetch is only a note: it is never evidence, and a cited page still needs a stored record.
  Some URLs answer 200 with a page that is not the one requested, such as a script stub or a redirect to a login page or a site's home page.
  A page is flagged when its text is under 300 characters (the stub that prompted the check was 209, and a login form is about 100 to 250, while a page worth citing has thousands and even a short government notice with its navigation reaches 400 or more), when it redirected to a site's home page (`/`, `/index.html` or a language root such as `/en`) from a deeper path, or when it redirected to a login, sign-in, single sign-on or consent path or host (`/user/sign-in`, `idp.nature.com`) from a page that is not one.
  A change of host alone is not flagged, since a DOI or an agency's new domain legitimately lands elsewhere.
  `fetch` prints a warning for a flagged page but still stores it, `status` marks it as not citable, and `submit` rejects a source that cites it with the reason.
  The flag is computed from the stored record each time, never saved, so the warning and the rejection agree (`pipeline/agent/page-check.ts`).
- `places` searches the gazetteer like the API path's `find_places` tool.
  `--query` may be repeated to search several names in one call, each result headed by its query.
  The commands import nothing that loads the Anthropic SDK (`replaceConflict` lives in `pipeline/generate/replace.ts` for that reason), which keeps a call under a second; importing `pipeline/generate/run.ts` made every call take several.
- `submit` parses, assembles and checks the draft with the same function as the API path's `submit_draft`: every `content:check` rule and every rule the pipeline adds.
  The retrieved URLs it checks sources against are those of the session's evidence records whose text still matches its hash; a record that does not, or that `fetch` did not write, is a problem of its own and never counts.
  Problems come back as a numbered list with exit code 1, and the subagent fixes them and submits again; the subagent's own budget bounds the repairs.
  Every submission is kept in `submissions/<n>.json`.
  A passing draft is written to the session's content directory by the same writer as the API path, after the same refusals as `start`.
  `submit --dry-run` runs the same refusals and checks and prints the same problems, or says the draft would pass with its story, source and pending reference counts.
  It writes nothing to the content tree, keeps no submission, changes nothing in the session and never finishes it, so a drafter can check a draft (for example its map routes) before submitting.
- `status` lists the fetched pages, the failed fetches and the submissions.

The evidence rule is stricter than the API path's: a cited URL must have been read through `fetch` in the session, so a search result never counts, and neither does WebFetch, which returns a model's summary instead of the page.
The subagent could in principle write the files the commands own; the hash catches an edited record, and the claim check, which reads every cited source again (through the API, or in a claim-checker subagent with every quote verified against a live fetch), is the independent audit before review, as it is for API drafts.
Agent drafting writes whole countries, including one that review sent back as a whole; a single story sent back is redrafted with `content:generate -- --revisions`.

### Agent claim check

`npm run content:claims-agent` lets a Claude Code subagent do the claim check in place of an API conversation, so it is paid by a Claude subscription instead of API credit.
The subagent reads the cited pages and judges each unit; code verifies every quote against a fresh fetch of the page, so the authenticity of a result rests on the pipeline, not on the subagent.
`.claude/agents/claim-checker.md` defines the subagent: Opus, with Bash, Read, Write, Glob and Grep, and without WebSearch or WebFetch.
Ask Claude Code to run it for a country, or once for each session `start` prints; sessions share no units, so several subagents can check one country at once.
It never reads the drafting session or draft notes, so the check stays independent of how the text was written.
The API claim check stays as a reserve and writes the same results.

```sh
npm run content:claims-agent -- start CHL [story] [--recheck] [--drafts] [--sources-per-session <n>] [--content-dir <dir>] [--claims-dir <dir>] [--model <id>] [--effort <label>] [--fresh]
npm run content:claims-agent -- fetch <session> "<url>" [--offset <n>] [--find <words>] [--refresh]
npm run content:claims-agent -- submit <session> [<verdicts.json>] [--dry-run]
npm run content:claims-agent -- status <session or country>
```

- `start` picks the due units with the API path's plan (`claimsJobs` in `pipeline/claims/plan.ts`): units without a result for their current text, or every selected unit with `--recheck`.
  It packs them into sessions of at most `--sources-per-session` cited sources (10 by default), exactly as the API path packs conversations, and creates them all at once, one directory each in `pipeline/.cache/claims-agent/<session>/`, named like `CHL`, `CHL-length` or `CHL-part2`.
  Planning every part from one reading of the claims file is what keeps parts apart: if each subagent planned its own part, a result saved in between would shift the packing.
  It refuses while an unfinished session of the country holds a unit it would hand out; such a session can be continued by another subagent, or discarded with `--fresh`.
  Each session has `session.json` (the units by ID and key, the sources, model, effort, prompt version, fetches and submissions) and `brief.md`.
  The brief is the claims-agent-v2 system prompt and task, rendered from the same values as the API task (`claimsTaskValues` in `pipeline/claims/session.ts`), followed by the commands and the JSON Schema of the verdict file, which is the schema of the API path's `submit_verdicts` tool.
  Its prompts are their own version line, `pipeline/prompts/claims-agent-v<n>/`: claims-agent-v1 is claims-v1 with the reading and submission instructions rewritten for these commands, and every judging rule unchanged (a test compares the two from `# Verdicts` on).
  claims-agent-v2 adds what the quote check ignores and what it enforces (the 300-character gap, quotes under 30 words, PDF line-end hyphens, lost ligatures and page breaks), how `--find` pages its matches, and to read a long page with `--offset` instead of saving it; claims-agent-v1 stays as it was for the results that recorded it, and a session keeps the version it started with.
- `fetch` reads one of the session's cited URLs (compared normalized; any other URL is refused) with the same fetcher and limits as agent drafting: HTML, plain text, and PDFs by their text layer, printed 20,000 characters at a time, with `--offset` and `--find`.
  It keeps a reading copy in `pages/`, so reading the next part does not fetch the page again, and logs every fetch and failure in `session.json`; the copy is never used to verify anything.
  It warns when the page is probably not the cited one, by agent drafting's page check (`pipeline/agent/page-check.ts`: a stub, or a redirect to a login or home page).
- `submit` validates the verdict file with the API path's `checkVerdicts`: every unit still due and its sources answered once, a source reported read was fetched with the fetch command in this session, `supported` has no unsupported phrases and the others do, every unsupported phrase is copied from the unit, quotes come from the unit's own read sources, and `source_unreachable` names an unreadable source.
  It verifies the quotes itself: it fetches every page quoted from a source reported read, live from the web at that moment, and matches each quote against that text with the API path's matcher (`normalizeForMatch` and the `QUOTE_MAX_GAP` bound on each gap).
  A quote that is not on the live page, or whose parts are too far apart there, fails its unit, and so does a quote from a page the live fetch cannot read; such a unit becomes "source unreachable" only when the subagent marks the source unreachable and gives that verdict.
  A live page that the page check flags counts as unreadable, so a cited URL that now redirects to a home page cannot verify a quote even when that page happens to repeat the text.
  Unlike the API path, a quote from a PDF is checked too, against the PDF's text layer.
  Every unit that passes is saved at once by `recordChecks`, into the same `content/en/claims/<slug>.json` in the same format, and the others are listed with their problems.
  The subagent fixes them and submits again; a unit that passed may stay in the file, and a new verdict replaces its saved one only if the new one passes.
  A subagent may also stop with units left not checked, which stay due for the next session.
  A submission is refused when a unit's text or sources changed since `start`, because its verdict would no longer apply.
  It prints one line per live fetch with the length of the text and whether it is the text of the reading copy, and a summary of how many units were checked, how many passed and were saved, and how many failed.
  When a quote is not on the live page and the live text differs from the reading copy, the problem says so, with both lengths and the time of the copy, so a page that served the subagent one text and the live fetch another is told apart from a miscopied quote; the reading copy explains a failure and never verifies a quote.
  Every verdict file is kept in `submissions/<n>.json`, and the session logs each submission's saved units, problems and live fetches (URL, time, length and SHA-256 of the text, or the error).
  `--dry-run` runs the same checks and live fetches, and saves, keeps and logs nothing.
- `status` lists the units checked and still due (with the last problems), the fetched and unfetched sources, the failed fetches and the submissions; given a country, every session of it.

An agent result is an API result with three differences.
Its `promptVersion` is `claims-agent-v2` (`claims-agent-v1` on earlier results), and its `effort` is what `start` recorded ("default", the subagent's own, unless given); `model` is the subagent's model (`claude-opus-5-5` by default, `--model` to change).
An extra `verification` field lists, for each source the unit quotes, the URL, the final URL, the time of the live fetch, and the length and SHA-256 of the text its quotes were matched against; it is empty when the verdict quotes nothing.
`content:review -- show` prints both kinds the same way, adding the prompt version and the live fetch to an agent result, and `approve` gates on them identically: a missing or flagged result blocks approval until the text is revised or the flag accepted with `--accept-claims`.

The guarantee: every quote of a saved agent result was on the cited page, as the matcher compares text, when the pipeline fetched it live at submission.
The subagent can write any file in its session, but none of them is read to verify a quote.
What the subagent judges is support, whether the quoted text and the rest of the page state the unit; that is the judgement the API check asks of Claude, made here by the subscription model.
A page can change after submission; the SHA-256 records which text was checked.
A subagent could still call a unit `not_supported` without reading its source, which only flags it for review, or pass a unit on a real quote that does not state it, which is the same misreading risk as the API check.

## Globe

A framework-free controller in `src/globe/`, driven by a declarative `MapScene`, with a thin React wrapper.

```ts
const globe = createAtlasGlobe(container, { labels, messages, assets, occluders, homeView });
globe.setScene(scene); // MapScene: camera?, focusCountryId?, highlights, places, routes, focusPlaceId?
globe.zoom('in' | 'out' | 'reset');
const off = globe.on('select', (countryId) => {}); // also 'focusPlace' (place id) and 'status'
globe.status; // 'loading' | 'ready' | 'error'
globe.dispose();
```

```tsx
<GlobeView ref={handle} scene={scene} labels={labels} messages={messages}
  occluders={findPanels} onSelect={...} onFocusPlace={...} onStatus={...} />
handle.current?.zoom('in');
```

`MapScene` (`src/globe/scene.ts`) carries resolved coordinates: the content layer looks places up in the gazetteer before it builds a scene.
An empty scene is the world view.
Options carry everything the controller needs, so it never imports app or content modules:

- `labels`: country id, name, anchor, area, and label rank, read once at creation.
- `messages`: the interface strings the globe shows, such as the accessible names of labels ("Explore {name}") and the failure fallback; `GlobeStage` builds them from the `globe` area of the message catalog, so the globe never imports `src/i18n/`.
- `assets`: the basemap image and both geometry URLs; `DEFAULT_GLOBE_ASSETS` points at `public/maps`.
- `occluders`: a callback returning elements, such as panels, that labels must not cover; they are measured at each layout and observed, so a panel resizing on its own re-runs layout.
- `homeView`: the camera for a scene with no camera and no focus country.

How a scene is applied:

- Scenes are diffed (`scene-diff.ts`); a structurally equal scene does nothing, and each changed layer updates on its own.
- The camera moves only when the scene's target view changes.
  The target is the focused place, else the explicit `camera`, else a view framed from the focus country's area (`camera.ts`), else home.
  Reset returns to the scene's view without the focused place.
- Country names are created once and updated in place.
  Place labels and routes are keyed by id, so navigation only creates, moves, or removes the ones that changed.
- A place with a country's id or name replaces that country's name, and the focus country is never repeated as a place.
- Highlights light up as one merged fill and outline per role (`related`, `contrast`), and highlighted names win label collisions.

How labels are laid out:

- Country names and place labels share one collision space with a fixed priority: the selected country, then the scene's places (focused, then water, then the rest), then other countries by emphasis, label rank, and on-screen size.
  An earlier label always wins, and each layout starts from an empty space, so no position survives a scene change.
- The scene's places are placed first and the selected name steps around them, shifting above or below its point; only when nothing else fits does the selected name go first, preferring space clear of the places' points, and the places step around it.
- Each country has up to six candidate points (`label-candidates.ts`): the Natural Earth label point, then well-spread interior points of its largest parts, ranked by open room around them and skipping thin tails.
  A long country also gets the most open point of each third of its length, so Vietnam, Chile, Norway and Italy can be named from whichever stretch is in view.
  They are computed once per country from the geometry loaded at the time, so layout itself never scans polygons.
- Points are tried in order of the open land they show: their room, foreshortened by the view and weighted by the label's horizon fade, so a country near the horizon is named from its visible side.
  A visible name keeps its current point while that point faces the camera and shows at least three quarters of the best point's score, so names hold still while the camera moves but move on once it settles elsewhere.
- Names are placed in two passes.
  In the first, a name must fit inside: land of that country under the center and four corners of its ink box, inside the map frame, and clear of occluders and earlier labels.
  A near miss may shift a small step away from the failing corners, a name whose spot is taken may step a little to either side or up or down, and a multi-word name may break onto two lines.
- The names left over then try an overflow fit, as an atlas letters a narrow or island country across the water beside it: the center must be on the country's own land, and the points halfway from the center to each end on that land or at sea.
  Only the ends may reach over a neighbour's edge, never its interior, and since this pass runs after every name that fits inside, an overflowing name never displaces one.
- A water place sits on water: of the small shifts around its point that are clear of earlier labels, it takes the one with the least land under it, and its center is never on land.
  A strait or a small bay may reach over a shore (at most three of nine sample points on land); when every shift covers more, the label is left out at that zoom unless the reader focused it.
- Rotated names along a country's axis were considered and not built: the collision space is axis-aligned rectangles, and rotation would need oriented boxes and a per-frame angle for every name.
  The stretch candidates and the overflow fit name the long countries without it.
- Names use short atlas forms: `scripts/build-countries.mjs` writes Natural Earth's short `NAME` ("Russia", "Dem. Rep. Congo") as `shortName` in `data/geo/countries.json` when it is shorter than the full name, the label index carries it, and the full name stays the accessible name.
- Type steps with zoom (11px at world zoom, 13px at regional zoom, the base size closer in); sizes are measured once per step, in a hidden host for names globe.gl has not attached yet.
- Visible names get slightly less padding and a small priority bonus, so names do not flicker as the camera moves.
- Every point-in-country test, for picking and for layout, is a planar even-odd test on the Natural Earth rings (`country-lookup.ts`), which are drawn in longitude and latitude and cut at the antimeridian.
  Each part keeps its bounds and the lookup buckets countries by ten-degree cells, so a test costs microseconds rather than the 100 or so of a spherical one, and a full layout stays near 1 to 3 ms (median) against the 48 ms budget.

Modules:

| Module | Responsibility |
| --- | --- |
| `controller.ts` | Public API, events, lifecycle; loads the engine on demand |
| `engine.ts` | globe.gl setup, render settings, resize, visibility, context loss; composes the parts below |
| `camera.ts`, `scene-diff.ts` | Pure framing and change detection |
| `geography.ts` | Country geometry, borders, fills, picking, detail refinement |
| `borders.ts`, `fills.ts`, `country-lookup.ts`, `projection.ts` | Merged line buffers, lazy merged caps, planar point-in-country tests and lookup, sphere unprojection |
| `label-layer.ts` | Label elements, scene updates, measurement, occluder rectangles |
| `cartography.ts` | Pure label layout: candidate order, priority, inside and overflow fits, water placement, nudges, collisions, two-line breaks |
| `label-candidates.ts` | Interior label points per country |
| `interactions.ts` | Pointer hover, tooltip, click selection |
| `route-layer.ts` | Route paths styled by kind |
| `materials.ts` | Image basemap material and camera-relative lights |
| `GlobeView.tsx`, `globe.css` | React wrapper, failure fallback, globe-owned styles |

Why:

- The prototype kept all globe logic inside one large React effect and passed functions between effects through refs.
  A controller with explicit methods is easier to read, test, and reuse.
- React state describes *what* to show (`MapScene`); the controller decides *how* to animate and render it.
- globe.gl and Three.js load through a dynamic import inside the controller, so the wrapper is safe to server-render and the engine stays out of the initial bundle.

Kept from the prototype, because each was measured or verified:

- The 4K image basemap with merged border buffers, rather than vector land meshes.
- Progressive country labels with screen-space fit, horizon fading, and collision checks, laid out at most every 48 ms.
- Sphere-intersection picking with bounds filtering, instead of scene raycasts; globe.gl pointer interaction stays off.
- Lazy, merged fill caps for hovered and selected countries, with a bounded sixteen-country cache.
- Base geometry first, detailed geometry once the camera is closer than altitude 1.1.
- Hover paused while the camera moves, and drags never select, on the globe or on labels.
- Reduced motion skips camera tweens and route animation.
- Pixel ratio capped at 2, rendering paused while the tab is hidden, and WebGL failure or context loss shown as a fallback that keeps the stories usable.
  Retry mounts a fresh controller instead of reloading the page.
  While the fallback shows, the panel still lists a story's map places, but the chips are disabled and the hint to tap them is hidden, since there is nothing to find them on.

Removed: the vector terrain mode, relief textures, the label toggle, and the FPS diagnostic panel.
They were investigation tools, not product features, and they remain in git history.

What can go wrong:

- globe.gl recreates every label element when its `htmlElement` accessor changes, so it is set exactly once.
- globe.gl applies a new size to its camera in a debounced update, so layout waits until the camera's aspect matches the size; projecting earlier puts names in the wrong place.
- globe.gl writes every label's `transform` each frame, so a CSS transition on `transform` makes labels trail the globe and cross each other; the interface button rule in `app/globals.css` leaves out everything inside `.globe-host`, and label styles transition colors only.
- A country whose name fits neither inside nor across its own coast, such as a small landlocked country between larger names, stays unnamed until the camera comes closer.

## Server and client boundary

Content modules (`src/content/`, `content/`, `data/geo/`, zod) are server-only and never enter the browser bundle.
Pages are server components: they load content at build time and pass small, already-resolved view models (the story or country to read, its resolved `MapScene`, its next questions with titles) to client components.
The persistent shell in the root layout does not load content itself; the current page hands it the scene and destination through a small client bridge component.
Data the client needs across pages is generated at build time as compact indexes: country labels for the globe, and a search and title index for search, the library, and recent history.

Why: the question bank grows to well over a thousand stories.
Bundling it, the gazetteer, and zod into the client would cost megabytes on every visit, while each page only needs one story.

How it is enforced:

- `src/content/index.ts` imports `server-only`, so a client component that reaches content fails the build.
  Vitest aliases `server-only` to an empty module so tests can load content directly.
- ESLint (`no-restricted-imports` in `eslint.config.mjs`) forbids client code (`src/ui`, `src/globe`, `src/i18n` and the client-safe domain modules) from importing zod, content, `data/geo`, or the server-only domain modules.
  Type-only imports of content types are allowed.
- Domain modules are split by side.
  `page-views.ts`, `client-indexes.ts`, `slugs.ts` and `paths.ts` are server-only.
  `view-models.ts`, `destination.ts`, `atlas-index.ts`, `search.ts`, `ask.ts`, `live-answers.ts` and `library.ts` are client-safe and import no content.

How a page reaches the shell:

- `src/domain/page-views.ts` builds a serializable view model for each route (`buildCountryPage`, `buildStoryPage`, `buildHomeView`); the types live in `src/domain/view-models.ts`.
  A view model carries hrefs and display text, so the client never resolves IDs against content.
- The page renders `<ShellBridge page={view.shell} />` next to its panel.
  `ShellBridge` publishes `{destination, scene}` to `AtlasProvider` in an effect and withdraws it on unmount, unless a newer page has already replaced it.
  The home and not-found pages publish `null`, which is the world view.
- Focus on a map place is shell state keyed to the destination, so it resets when the destination changes and survives a re-render of the same page.
- The breadcrumb and map caption are part of the page, so they arrive with the server-rendered HTML rather than after hydration.
- Shell layout reacts to the page with CSS (`.world-app:has(#country-reading)`) instead of a class set from client state, so the first paint is already correct.
- The shell's grid lives in CSS variables on `.world-app` (`--gutter`, `--header`, `--footer`, `--inset`, `--panel-width`), so the header, panel, breadcrumb, caption, home column and map controls share one set of edges at each width.
- The globe labels avoid the elements in `OCCLUDERS` (`src/ui/shell/GlobeStage.tsx`) by their boxes, so those boxes must match what is drawn: each child of `.home` is only as wide as its content, except the input and the suggestions, which are drawn full width.

Client indexes are static route handlers (`dynamic = 'force-static'`), written to `out/atlas/` at build time and fetched once, on demand:

| Index | Built by | Used by | Size (raw / gzip) |
| --- | --- | --- | --- |
| `/atlas/labels.json` | `buildCountryLabels` | globe labels; the globe mounts once it loads | 29 KB / 9 KB |
| `/atlas/index.json` | `buildAtlasIndex` | question input and search, library, recent history, trail drawer, resume | 48 KB / 12 KB |

The atlas index holds every country, every question with its path, category, summary, build-time keywords (TF-IDF over the story text) and paraphrase words (the words of its paraphrases that the question lacks, each once, without stop words), every trail with its stop paths, and the home screen's suggested questions (offered when a query is not answered).
Paraphrase words cost about 125 bytes per question (40 gzipped), less than half of shipping the phrasings whole, because search matches words, not sentences.
It grows with the question bank, so it can be split by country if it gets too large to load whole.

## Discovery and navigation

- Paths are the source of truth for the current destination: `/`, `/<country>`, `/<country>/<story>`.
- Starter questions, next questions and the home screen's suggested questions come from content (`starterStoryIds`, `next`, `content/en/home.json`), not from hardcoded lists in code.

The question input:

- The home page leads with one question input ("What are you curious about?") over the globe, a few suggested starting questions below it, and a quieter "continue" line and trail link under those.
  The header search (Cmd/Ctrl K) opens the same component, `QuestionSearch` in `src/ui/search/`, so both rank, group and render results identically.
  Its shortcut label reads ⌘ K on Apple platforms and Ctrl K elsewhere; pages are prerendered without knowing the platform, so `useApplePlatform` decides after hydration and both labels share one cell, keeping the button's width stable.
- Results appear as the reader types, from the atlas index, which loads when the input first gets focus.
  Arrow keys move through them, and Enter opens the highlighted result, which starts at the top result for each query.
- `src/domain/search.ts` scores countries (names and native names), map identities, and questions (text, paraphrase words, category, summary, keywords).
  A matched term scores 3 anywhere in a question's words and 1 more when it is in the question or its paraphrase words, so a reader's own wording counts like the question's.
  Paraphrases let a question phrased with none of a story's words still find it ("Why is Singapore loaded?" finds the wealth story), while the coverage rule below keeps near misses unanswered.
  Words match by prefix, so a partly typed word already finds results; a small synonym list matches whole words only, so "Why is Singapore so rich?" finds the wealth question without "port" matching "Portuguese".
- `src/domain/ask.ts` turns those results into what the input shows.
  A query that reads like a question (a question mark or an opening question word) lists questions first; a place name, or the start of one, lists countries first.
  A question counts as answered only when one question covers its terms (both terms of a short query, all but one of a longer one), and, if the query names edited countries, only their questions qualify.
  Questions that answer the query lead the list, so Enter never opens a near miss.
- An unanswered question says so plainly: the atlas has not answered it yet, because every answer is sourced and reviewed.
  Nothing is highlighted and Enter does nothing until the reader moves to a row.
  It then offers the closest questions (those about a country the query names first), the countries the query names, and, when nothing is close, the suggested starting questions.
  There is no generated answer in Stage 1.
- `src/domain/live-answers.ts` defines the seam for Stage 2: a `LiveAnswerProvider` that takes the question and returns a story view model, or nothing.
  The unanswered outcome is where it would be called; nothing implements it yet.
- Before anything is typed, the dialog offers the other questions about the place being read and the suggested starting questions; the home input shows nothing until the reader types.

Reading:

- A country overview stays brief: the short story, its starter questions right after it, any further questions behind a disclosure, quick facts, the map connections, and then "why it matters" and sources behind disclosures.
- A story ends with its sources, the current trail's next stop when on a trail, and at most three next questions.
  Each next question says whether it goes deeper into the same place or elsewhere (with the other country's flag and the reason from content); same-place questions come first, and the one the trail already points to is left out.
- The panel footer always offers a new question by opening the search dialog.
- Share sends the page's title and link to the system share sheet on touch devices that have one, and copies the link everywhere else.
  Closing the share sheet does nothing; if the sheet or the clipboard is refused, a dialog shows the link to copy by hand (`src/ui/atlas/share-link.ts`).
- A map-only country shows its basics and the nearest edited countries, measured between label anchors.
- Bookmarks and recent history stay in localStorage, behind a small `library` interface so Stage 2 can add sync.
  They store destinations by ID and resolve titles and links through the atlas index; entries whose question no longer exists are hidden.
- Prototype query URLs redirect on Vercel; see [Platform](#platform).

## Styling

- Tailwind v4 serves the shadcn primitives in `src/ui/primitives/`.
  Everything else is plain CSS, one stylesheet beside the components it styles, imported by those components: `src/ui/shell/shell.css`, `src/ui/panel/panel.css`, `reading.css`, `map-overlays.css`, `map-connections.css` and `story-link.css`, `src/ui/dialogs/dialogs.css`, `src/ui/home/home.css`, `src/ui/search/search.css`, and `src/globe/globe.css`.
- `app/globals.css` keeps only the design tokens, base element styles, and the shell's grid.
  `.world-app` sets `--gutter`, `--header`, `--footer`, `--inset` and `--panel-width` for each screen size, and `.globe-area` is placed from them, so everything that reads those variables follows.
  On phones it also sets `--panel-strip`, the height of the reading panel collapsed to a strip; the panel's collapsed state lives in the panel itself and the grid reads it with `:has(#country-reading .panel-compact)`.
- Each class is styled in one place.
  A breakpoint adjusts a rule inside that rule's own stylesheet, instead of overriding it later in another one, so a rule's final value can be read where it is written.
- The breakpoints are 1500px, 1100px, 800px (phones, where every control is at least 44px) and 380px, plus short screens (800px high) for the globe and the home column.
- Our rules are unlayered, so they beat Tailwind's layered utilities on the shared primitives without `!important`.
  Use `!important` only to beat a more specific rule.

## Internationalization

English only in Stage 1.
Interface strings go through a typed message catalog in `src/i18n/` keyed by stable message IDs, not by English text.
Adding Chinese later means adding a catalog and a `content/zh/` tree, with no component changes.

## Testing

- Unit tests (Vitest) for pure logic: schema rules, navigation, search, cartography, picking.
- Content validation runs in CI on every change to `content/`.
- Pipeline tests in `tests/pipeline/` run plan, draft, verify, review, redraft and the paraphrase step on replayed model responses, and agent drafting and the agent claim check against stubbed page fetches.
- Playwright e2e in `e2e/` drives Chromium against the static export in `out/`, as shipped: ask, read an answer and its sources, follow a next question, Cmd/Ctrl K, deep links, not-found, robots.txt, the sitemap and canonical links, back and forward, trails, saving a story to your atlas, share, and the About sheet.
  A phone project runs the core loop (home, ask, story, follow), the reading panel collapsing to a strip and giving the globe its room, and share through a stubbed system share sheet at 390 by 844 with touch.
  Every page loads with the production response headers from `vercel.json`, and a Content Security Policy violation fails the test, like an uncaught error does.
  `npx serve` cannot apply the prototype query URL redirects, so `tests/deployment.test.ts` covers those against the compiled Vercel routes instead.
  The specs find things by role and visible text, read expected questions and sources from `content/en/`, and never depend on globe pixels or on WebGL (one spec runs with WebGL disabled).
  Run `npm run build` first, then `npm run test:e2e`; CI runs it as its own `e2e` job and keeps the Playwright report when it fails.
  CI runners have no GPU and render the globe in software, so tests there get twice the local time limits.
